## 1. PM 角色定位与 RACI 矩阵

### 1.1 PM 在项目中的角色

PM 不是"传话筒"，而是**产品方向的决策者**和**跨角色协调者**：

| 维度 | PM 的责任 |
|------|----------|
| **方向** | 定义产品愿景、目标用户、核心价值 |
| **需求** | 收集、过滤、优先级排序、写 PRD |
| **协调** | 拉通开发/测试/设计/运维/业务方 |
| **决策** | 在模糊地带拍板（功能范围、验收标准、上线时机）|
| **数据** | 设定指标、监控数据、推动迭代 |
| **用户** | 代表用户声音、避免技术驱动的过度设计 |

### 1.2 RACI 矩阵（4 角色 × 关键活动）

RACI = **R**esponsible（执行）/**A**ccountable（最终负责）/**C**onsulted（咨询）/**I**nformed（知情）

| 活动 | PM | 开发 | 测试 | 运维 |
|------|------|------|------|------|
| 需求收集 | R | I | I | I |
| 写 PRD | **A**/R | C | C | I |
| 需求评审 | **A** | R | R | C |
| 技术方案 | C | **A**/R | C | C |
| 估算工时 | C | **A**/R | C | I |
| Sprint 计划 | **A** | R | R | C |
| 设计稿 | **A**/R | C | I | I |
| 开发 | I | **A**/R | C | I |
| 单元测试 | I | R | C | I |
| 集成测试 | C | R | **A**/R | I |
| UAT 验收 | **A**/R | C | R | I |
| 性能评估 | C | R | R | **A**/R |
| 灰度发布 | **A** | C | C | R |
| 监控告警 | C | R | I | **A**/R |
| 数据分析 | **A**/R | C | I | C |
| 用户反馈 | **A**/R | I | I | I |
| 路线图规划 | **A**/R | C | C | C |

### 1.3 不可越权

PM **不**做的事（避免角色混乱）：
- ❌ 不写代码（即使会）
- ❌ 不直接修改数据库/服务器
- ❌ 不绕过测试直接上线
- ❌ 不承诺"绝对没问题"（业务方要的是概率和数据）
- ❌ 不替开发排期（提供优先级，估算和排期是开发的事）

### 1.4 PM 的 OKR 目标（v3.2 → v4.0）

**O1：构建一个学生真正爱用的 AI 学习伙伴**
- KR1：DAU ≥ 50（上线 1 个月内）
- KR2：用户平均对话轮数 ≥ 5（深度使用）
- KR3：用户 NPS ≥ 40

**O2：跑通完整业务闭环**
- KR1：完成 4 个核心功能（聊天/出题/词汇/进度）
- KR2：多用户上线（注册→使用→留存）
- KR3：所有功能跑通端到端 E2E

**O3：建立数据驱动的迭代机制**
- KR1：所有核心功能埋点
- KR2：建立 5 个核心指标看板
- KR3：完成 2 次以上 A/B 测试

### 阶段 3：需求评审（Sprint 启动前，1-2 小时）

**会议结构**：
```
14:00-14:10  PM 介绍 PRD（10min）
14:10-14:30  开发提问 + 工时估算（20min）
14:30-14:40  测试提问（10min）
14:40-14:50  运维提问（5min）
14:50-15:00  决策（accept/defer/reject）
```

**会议产出**：
- ✅ Approved：进入 Sprint Backlog
- ⏸️ Deferred：移到下个版本，原因记录
- ❌ Rejected：明确不做，原因记录
- 🔄 Revise：PM 改完再评审（24h 内）

**会议纪要模板**：
```markdown
# {PRD 名} 评审纪要
- 时间：YYYY-MM-DD HH:MM
- 参与：@PM @dev1 @qa @ops
- 决策：Approved（条件：xxx）
- 工时估算：dev 5d / qa 1d
- 风险：M3 出题成功率低，需备用方案
```

### 阶段 5：UAT 用户验收（每个功能/版本，1-3 天）

PM 主持，与真实用户或内部用户一起：

**UAT 流程**：
1. PM 准备 UAT 用例（基于 PRD 验收标准）
2. 邀请 3-5 个用户（学生 / 家长 / 老师）
3. 真实场景操作 + 反馈
4. 收集问题清单，分类（P0/P1/P2）
5. 决策：上线 / 修后再上 / 延期

**UAT 用例模板**：
```
功能：完形填空测试
用例 1：基础流程
  前置：已注册用户
  步骤：
    1. 进入 /quiz
    2. 选择"完形填空"题型
    3. 选择 Unit 3
    4. 点击"开始测试"
    5. 答完 5 题
    6. 提交批改
  期望：
    - 5 题能正常显示
    - 批改后显示分数 + 解析
    - 进度页能看到这条记录
```

**UAT 反馈表**：
| 用户 | 反馈 | 严重度 | 状态 |
|------|------|--------|------|
| 张同学 | 出题偶尔失败 | P1 | 修 |
| 李同学 | UI 不够清晰 | P2 | 改 |
| 王老师 | 想看班级汇总 | P3 | 下版本 |

## 3. 用户研究与数据驱动

### 3.1 用户画像（Persona）

针对本项目（八年级英语 AI），定义 3 个核心 Persona：

#### Persona 1：小张（主动学习型学生）
- **背景**：八年级，13 岁，成绩中上
- **目标**：提高英语成绩，准备中考
- **痛点**：单词记不住、语法搞不懂、家长没时间辅导
- **场景**：放学回家自主复习 1 小时
- **预期行为**：每天用聊天问答 3-5 个语法点，每周做 1-2 次测验
- **愿付费意愿**：低（学生无收入），靠家长买单

#### Persona 2：张妈（辅导型家长）
- **背景**：35-40 岁，本科，自己英语还行但没法教
- **目标**：监督孩子学习，看到进步
- **痛点**：不知道孩子学了什么、错在哪里、进步多少
- **场景**：晚上 9 点看孩子做作业时
- **预期行为**：偶尔查看孩子进度、对话历史
- **愿付费意愿**：中（每月 20-50 元）

#### Persona 3：李老师（教育者）
- **背景**：英语老师，30+，带 2 个班
- **目标**：提高自己班学生成绩、找新教学辅助
- **痛点**：批改作业占时间、个性化辅导难
- **场景**：备课、出题
- **预期行为**：可能用"出题"功能备课
- **愿付费意愿**：中（学校/机构买单）

### 3.2 用户旅程地图（学生 Persona 1）

```
[认知]     [首次使用]    [习惯养成]    [深度使用]    [留存/流失]
抖音视频    注册         每天用一次    每天3-5次     持续或卸载
↓
"咦"        "试试看"      "今天做了吗"  "我的进度"    续费/流失
↓
落地页      /login       闪卡复习      /progress     价值感知
↓           ↓            ↓             ↓              ↓
5秒决定     30秒上手     7天习惯       30天深入       90天评估
```

**关键触点**：
- 首次注册体验：决定是否留下
- 第一次对话质量：决定是否第二天还来
- 第一周使用频次：决定是否形成习惯
- 第一个月累计：决定是否付费

### 3.3 数据指标体系

#### 3.3.1 北极星指标

**北极星**：`每周完成测验数 × 平均分`

- 选这个的理由：直接反映"产品在帮学生提分"
- 周为单位：避免日活波动

#### 3.3.2 AARRR 海盗指标

| 阶段 | 指标 | 当前基线 | 目标 |
|------|------|---------|------|
| **Acquisition** | 日新增注册 | - | - |
| | 注册转化率（落地页 → 注册） | - | ≥ 20% |
| **Activation** | 首次完成对话 | - | - |
| | 首次完成时间（注册 → 首聊） | - | ≤ 5 min |
| | 7 日激活率 | - | ≥ 40% |
| **Retention** | 次日留存 | - | ≥ 30% |
| | 7 日留存 | - | ≥ 15% |
| | 30 日留存 | - | ≥ 8% |
| **Revenue** | 付费用户数 | - | - |
| | ARPU（月） | - | - |
| | LTV | - | - |
| **Referral** | 邀请率 | - | - |
| | NPS | - | ≥ 40 |

#### 3.3.3 业务指标（功能级）

| 功能 | 核心指标 |
|------|---------|
| 聊天 | 平均对话轮数 / 满意度 |
| 出题 | 完成率（开始 → 答完）/ 平均分 |
| 词汇 | 复习量 / 记忆度（mastery 分布） |
| 进度 | 访问率 / 薄弱单元使用率 |

### 3.4 埋点设计

**核心事件**：

```typescript
// 注册/认证
track("user_registered", { source: "direct" })
track("user_logged_in", { method: "password" })

// 功能使用
track("chat_started", { mode: "grammar", session_id: "..." })
track("chat_message_sent", { session_id, role: "user" })
track("chat_completed", { session_id, message_count, latency_ms, mode })

track("quiz_started", { unit: "Unit 1", quiz_type: "multiple_choice", count: 5 })
track("quiz_question_answered", { session_id, question_id, is_correct, score })
track("quiz_completed", { session_id, total_score, correct_count })

track("vocab_session_started", { unit: "Unit 1", semester: 1, word_count: 10 })
track("vocab_word_marked", { word: "...", mastered: true, mastery_level: 2 })

track("progress_viewed", {})
```

**埋点规范**：
- 必填字段：`event`、`timestamp`、`user_id`、`session_id`
- 不记：密码、token、个人敏感信息
- 通过 Sentry + PostHog 双写

### 3.5 用户反馈机制

| 渠道 | 工具 | 用法 |
|------|------|------|
| 应用内反馈 | Intercom Messenger | 浮动按钮，用户随时发 |
| 评分 | 应用商店 + 内置 5 星 | 触发条件：完成 5 次对话后 |
| 邮件 | Customer.io | 主动发调研 |
| 社群 | 微信群 / Discord | 早期用户聚集地 |
| 用户访谈 | Calendly + Zoom | 每月 3-5 个 |

**反馈处理流程**：
```
收集 → 分类（P0/P1/P2/feature）→ 排期 → 实现 → 通知反馈者
```

### 3.6 A/B 测试框架

**适用场景**：
- 提示词改版（如"通用问答"换成"亲切学伴"）
- UI 颜色/位置（如"出题"按钮放哪）
- 文案（如"开始测试"vs"挑战自己"）

**工具**（前期）：自建 + 配置开关
**工具**（后期）：PostHog Experiments / GrowthBook

**A/B 测试流程**：
1. PM 提假设：X 改版会提升 Y 指标
2. 配置：50% 用户看到 A，50% 看到 B
3. 跑 1-2 周（达到统计显著）
4. 决策：保留胜出版本 / 放弃 / 继续测

## 4. 需求与 PRD 模板

### 4.1 需求分层

```
Epic（史诗级）      → 大方向，跨多个 Sprint
  └─ Feature（特性）→ 一个完整功能（1-2 周）
       └─ User Story（用户故事）→ 一个可交付价值的小功能（1-3 天）
            └─ Task（任务）→ 工程师的具体动作
```

示例：
- Epic：让 AI 出题更智能
  - Feature：完形填空题型
    - User Story：作为学生，我可以选择完形填空并完成 5 题
      - Task：后端 API `/api/quiz/cloze`
      - Task：前端 cloze UI
      - Task：埋点 `cloze_started` / `cloze_completed`

### 4.2 需求来源

| 来源 | 例子 | 接收频率 |
|------|------|---------|
| 用户反馈 | 出题失败率高 | 每天 |
| 业务方 | 学校老师想要班级管理 | 每月 |
| 数据分析 | 7 日留存低 | 每周 |

所有来源进 Notion 需求池，**统一评估**。

### 4.3 优先级评分（RICE）

**RICE 公式**：
```
RICE Score = (R × I × C × E) / 100
```

| 字母 | 含义 | 单位 | 取值 |
|------|------|------|------|
| R | Reach（覆盖） | 单位时间内受影响用户数 | 例：1000 人/月 |
| I | Impact（影响） | 单用户对目标贡献 | 0.25/0.5/1/2/3 |
| C | Confidence（信心） | 把握度 | 0-100% |
| E | Effort（投入） | 人月 | 例：2 人月 |

**示例计算**：

```
完形填空题型
  R: 1000 学生/月
  I: 2 (显著提分)
  C: 80%
  E: 1.5 人月
  Score = (1000 × 2 × 80) / (100 × 1.5) = 1066

班级管理
  R: 50 老师
  I: 1
  C: 60%
  E: 3 人月
  Score = (50 × 1 × 60) / (100 × 3) = 10

→ 完形填空优先做
```

## 6. PM 与 4 角色的协作流程

### 6.1 与开发协作

**PM 提供**：
- 清晰 PRD（不让开发猜）
- 优先级（不让开发"做最炫的"）
- 决策速度（24h 内回应）
- 验收时间（不拖延）

**PM 接受**：
- 工时估算（不压价）
- 技术约束（不强行要实现）
- 重构建议（接受必要的）

**沟通频率**：
- 日常：Slack 异步
- 每周：Sprint 站会 15min
- 每 2 周：Sprint 评审 1h
- 不定期：技术方案 review

**冲突解决**：
- PM 主张"做"：开发答"做不了" → 找运维评估影响，找测试评估用户
- PM 主张"不做"：开发答"应该做" → PM 用数据说话

### 6.2 与测试协作

**PM 提供**：
- 验收标准（Given/When/Then）
- 边缘情况清单
- 真实用户场景

**测试提供**：
- 测试用例
- 自动化覆盖
- Bug 严重度评估

**沟通**：
- 提测前：PM 参与用例 review
- 测试中：每日同步进度
- 测完后：UAT 一起跑

### 6.3 与运维协作

**PM 提供**：
- 灰度计划
- 业务优先级（影响发布决策）
- 用户沟通

**运维提供**：
- 性能指标
- 发布建议（时机、风险）
- 故障影响评估

**沟通**：
- 每周：发布状态同步
- 紧急：直接 Slack
- 复盘：PM 主持

### 6.4 与业务方 / 用户沟通

**PM 是**：
- 用户声音的代言人
- 业务方对产品期望的传达者

**渠道**：
- 月度业务方 Review
- 双周用户邮件
- Slack 实时答疑（如果有客服）

**什么时候**：
- 新功能上线：通知 + 培训

- 改版：预告 + 收集反馈

### 7.2 留存提升策略

#### 激活（Aha Moment）
- 目标：注册 → 7 天内完成 1 次测验 + 拿到分数
- 手段：注册后引导页（"先做个 5 题小测"）
- 衡量：7 日激活率 ≥ 40%

#### 习惯（Habit）
- 目标：每天 1 次使用
- 手段：每日推送（"今天背 5 个新单词？"）
- 衡量：日活跃天数 / 总天数

#### 长期价值（Long-term Value）
- 目标：30 日留存 ≥ 8%
- 手段：进度可视化、成就系统、家长监控
- 衡量：LTV/ CAC 比率
